To divide **Stage 3** between two people, we can split the workload into **Feature Engineering (Person 3A)** and **Machine Learning & Inference (Person 3B)**. This is a very natural split in data science pipelines and allows both of you to work concurrently.

Here is the exact implementation plan and breakdown of who handles the GPU workload:

---

### Who has the GPU-Intensive Work?
**Person 3B (Model Training & Optimization)** has the **GPU-intensive** work. 
- Training a Gradient Boosted Decision Tree (like XGBoost, LightGBM, or CatBoost) on millions of candidate pairs from a 2.3 GB dataset requires massive parallel computation. 
- Libraries like XGBoost (`tree_method='gpu_hist'`) and LightGBM (`device='gpu'`) heavily utilize the GPU to accelerate tree building.
- Person 3A’s work (Feature Engineering) is heavily **CPU-bound**, as string matching algorithms (like Levenshtein distance and token overlap) rely on sequential text processing on the CPU.

---

### The New Division of Labor

#### 👤 Person 3A: Pairwise Feature Engineering (CPU-Heavy)
**Owned File:** `code/business_entity_resolution/src/features.py`

**Responsibilities:**
1. **Develop the Feature Extraction Logic:** Write the `extract_features(s1_rec, cand_rec)` function that takes a Source 1 record and a candidate record and returns a dictionary/array of numerical features.
2. **Text Similarity Metrics:** Use `rapidfuzz` to calculate Levenshtein ratio, Jaro-Winkler, Token Sort Ratio, and Token Set Ratio on business names and addresses.
3. **Geographical Features:** Create binary flags for exact PIN/ZIP code matches or mismatches.
4. **Output Contract:** Ensure your function returns a clean, standardized vector (e.g., a Pandas Series or NumPy array) that Person 3B can directly plug into their model.

---

#### 👤 Person 3B: Model Training & Threshold Optimization (GPU-Intensive)
**Owned File:** `code/business_entity_resolution/src/train_predict.py`

**Responsibilities:**
1. **Dataset Construction:** Write a script that iterates through the training candidate pairs, calls Person 3A's `extract_features` function, and assigns a label (`1` if the pair is in the ground truth, `0` otherwise) to build the `X_train` and `y_train` matrices.
2. **GPU Model Training:** Initialize and train an XGBoost or LightGBM classifier using GPU acceleration. You will train on the features engineered by Person 3A.
3. **Threshold Optimization (Crucial):** Run predictions on a validation set and test probability thresholds (e.g., `0.50` to `0.95`). Write a loop that calculates the **Macro $F_{0.5}$** score at each threshold, and save the threshold that produces the highest score.
4. **Final Inference & Submission:** Load the test candidates, run your model, apply the optimized threshold, and generate the final `output/matching_results.tsv` file adhering to the subset constraint.

---

### Global Rule 2: Handling Nulls & Missing Data (Person 3A)
Person 3A must guarantee that `extract_features` **never throws an exception**. 
- The dataset is noisy. Sometimes `business_address_clean` will be an empty string, or `name_tokens` will be empty.
- **Rule:** If a field is missing, Person 3A's code must catch it and return a default value (like `0.0` or `-1.0`). Person 3B's ML model (XGBoost/LightGBM) will handle these numeric defaults perfectly, but a Python `KeyError` or `TypeError` will crash a 4-hour training run.

### Global Rule 3: The "Mock" Implementation (Person 3B)
Person 3B cannot wait for Person 3A to finish writing complex RapidFuzz logic. To test `train_predict.py` independently, Person 3B should write a "Dummy" feature extractor at the top of their file on Day 1:
